## Fix 1 — delete + re-add no longer launders the failure backoff (review #1)

Failure state lived only on the `MonitoredUrl` row, so deleting it threw away the cooldown *and* the auto-pause, and the re-add bought another immediate fetch — repeatable indefinitely.

- **`app/models.py:288-410`** — new `UrlBackoff` table (`url_backoff`) parks `(user_id, url_key, consecutive_failures, last_failure_at, last_error)`, plus `backoff_key()` (folds scheme/host case and the default port; keeps path, query, non-default port), `remember_failure_state()`, `recall_failure_state()`, `_prune_backoff_memory()`. Reading **consumes** the entry, so a monitor that later succeeds can't be re-seeded with stale failures. Growth is bounded: nothing is written for a healthy or expired monitor, and `MAX_BACKOFF_MEMORY_PER_USER = 50` caps what's left per account.
- **`app/main.py:1191`** (`delete_url`) — parks the state before `db.delete`.
- **`app/main.py:973-1002`** (`add_url`) — inherits it onto the new row, re-applies the auto-pause at `FAILURE_PAUSE_THRESHOLD`, and **skips the immediate first check** when the inherited cooldown is still live.
- Existing databases pick up the table via `Base.metadata.create_all` in `init_db` (`app/main.py:198`); no `_ADDED_COLUMNS` entry needed.

## Fix 2 — `max_urls` is no longer racy across the await (review #2)

- **`app/main.py:952-959`** — re-counts the account's monitors immediately before `db.add(monitored)`, after the last await. The original pre-validation count stays as the cheap early reject.
